// what is adi

Not a chatbot. Not a scanner UI. An actual agent.

Adi keeps a persistent, typed model of the target — assets, services, endpoints, hypotheses, and evidence — and builds on it decision after decision, the way Claude Code understands a codebase instead of a single file.

🧠

Persistent target model

Every discovery — an open port, a header, an endpoint — is stored in a structured knowledge graph that survives across sessions.

🧩

Thinks in capabilities

Adi decides "I need to enumerate services," then resolves the best available tool for that job — not the other way around.

🔒

Isolated by default

Every tool runs in a capability-dropped Docker container with zero access to your SSH keys, credentials, or home directory.

✅

Hypothesis, then proof

A scanner alert is never auto-promoted to a confirmed finding — it goes through an explicit hypothesis → validation → evidence pipeline.

🎯

Bounded context, not noise

The planner never sees your whole database — only a tight, relevant summary: goal, assets, active hypotheses, and remaining budget.

🛑

Hard loop prevention

Action budgets, duplicate detection, and automatic shutdown after repeated failures — autonomy with real guardrails.

// safety model

Safety is enforced in code, not just in docs

Every target-facing action passes through a deterministic scope engine before anything executes — this is not a model judgment call.

→

Scope-checked execution. Any action against a host outside the authorized target list is blocked before it runs, not after.

→

Zero-access sandboxing. Tools run in a capability-dropped container — no SSH keys, no credentials, no home directory.

→

No destructive capability. No persistence mechanisms, no stealth/evasion techniques, no intentional denial-of-service.

→

No scope creep. A redirect to an out-of-scope host is recorded as an external dependency — never auto-followed for testing.

→

Secrets stay secrets. Test-account credentials are resolved from environment variables only — never logged, never in reports.

→

Hard budgets. Max actions, max consecutive failures, and duplicate-action detection stop runaway loops automatically.

// faq

Frequently asked questions

Can I point Adi at any website or server?

No. Adi is built strictly for systems you own or have explicit written authorization to test, plus CTF platforms and isolated educational labs. The scope engine technically blocks any action outside that boundary — it isn't just a policy, it's enforced in code.

How is this different from a vulnerability scanner?

A scanner hands you a list of raw alerts. Adi keeps a persistent model of the target, turns those alerts into explicit hypotheses, and only promotes one to a confirmed finding after actual validation — which dramatically cuts false positives.

Does Adi require an LLM connection to run?

Direct tool execution (e.g. running a port scan) works with no LLM at all. The autonomous planning loop needs a configured provider — Anthropic, or any OpenAI-compatible endpoint including OpenRouter or a local model.

Is it open source?

Yes — fully open on GitHub, developed in clearly documented phases: core runtime, the autonomous agent loop, web-focused tooling, a finding-verification engine, and source-to-runtime correlation.

Where does the name come from?

Adi is named after cryptographer Adi Shamir, co-inventor of RSA and one of the founding figures of modern cybersecurity.
